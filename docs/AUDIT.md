# Аудит проекта (этап 1 тотального обновления, 3.25.0)

Это первый из шести этапов тотального обновления:

1. **Стабилизация и аудит** — этот документ.
2. Архитектура и производительность.
3. Арт-дирекшн и библия мира.
4. VFX.
5. Подклассы и комбо.
6. Лор и квесты.

Здесь собрано:

* как устроен мод;
* где у него горячие пути;
* что исправлено в 3.25.0;
* что остаётся рискованным и в каком этапе будет исправлено.

## Как проверялось

Аудит статический. Собрать мод в среде разработки нельзя: к Maven Central, Forge, NeoForged, Mojang, GeckoLib и репозиторию PlayerAnimator доступа нет, политика сети запрещает их. **Код 3.19–3.25 ни разу не компилировался с настоящими jar Minecraft.** Это главный риск проекта (см. «Риски», п. 1).

Что проверено:

* `javac` по всем 316 файлам, без jar Minecraft. Учитываются только синтаксические ошибки: ошибки «не найден символ» неизбежны.
* `tools/validate.py`: ключи перевода, иконки, модели, анимации, профили эффектов, регистрация пакетов, а с 3.25 — ещё и правила этапа 1.
* `tools/balance_model.py --check`.
* Валидность всех JSON в ресурсах.

Всего 316 файлов и около 35 600 строк Java. Ассеты генерирует `tools/gen_assets.py`: Python пишет текстуры, модели GeckoLib, анимации, JSON и часть Java-классов с моделями.

**Поток данных игрока.** Всё состояние живёт в capability `PlayerRpgData`. В нём лежат:

* класс, уровень, ранги и модификации;
* `extra` — ресурсы активного класса;
* `stash` — прогресс остальных классов;
* `story`, `professions` и `kind`.

Пока данные «грязные» (`dirty`), сервер шлёт клиенту весь тег до 4 раз в секунду (`CommonEvents.tick`). Флаг `dirty` ставится в 136 местах.

**Поток эффектов.** Навык вызывает `Fx.at` / `follow` / `beam` / `beamPos` / `bolt`; таких вызовов 173. Каждый вызов создаёт серверную сущность `SkillFxEntity` с моделью GeckoLib. Клиент рисует её, приклеивая к цели по id каждый кадр (`SkillFxRenderer`).

## Что исправлено в 3.25.0

1. **Единая очистка статического состояния (`core/StateCleanup`).** Класс со статической картой регистрирует её очистку при первой загрузке: `static { StateCleanup.onStop(MAP::clear); StateCleanup.onLogout(MAP::remove); }`. Хуки выхода выполняются последними, после обработчиков самих классов.
   * Раньше при выходе или смене мира в одиночной игре не очищались:
     * потоки чернил и дыхания;
     * каналы удержания клавиши;
     * отслеживание ритуальных предметов;
     * позиции реликвий Одарённых;
     * ключи громоотводов;
     * состояние стола зачарования Духовного мастера;
     * связи Фамильяра-тома;
     * счётчики выживания.
   * Самое заметное следствие было у громоотводов: ключи хранились без имени мира. Поэтому настоящий громоотвод в **другом** сохранении на тех же координатах мог исчезнуть без дропа.
   * `validate.py` теперь падает, если в серверном коде появляется статическая карта с ключом-игроком (UUID, строка, отслеживаемый объект) без регистрации очистки.
2. **Бюджет эффектов (`Fx.allow`).**
   * Короткий эффект не создаётся, если рядом нет ни одного игрока (`fxCullDistance`, по умолчанию 96 блоков — та же дальность, на которой эффекты перестают рисоваться).
   * За один серверный тик создаётся не больше `fxMaxPerTick` эффектов, по умолчанию 192.
   * Длинные ауры (жизнь больше 200 тиков: венец Рыцаря Смерти, метки) не пропускаются никогда.
   * На урон, лечение и правила это не влияет: все 173 места вызова уже обрабатывали `null`.
   * Счётчики показывает `/rpg debug`.
3. **Меньше сетевого трафика от эффектов.** Клиент сам приклеивает следящие эффекты и лучи к сущностям каждый кадр, поэтому серверная копия нужна только как запасной вариант. Раньше она двигалась каждый тик, и каждый эффект слал пакет движения каждому наблюдателю. Теперь копия двигается, только когда отстала на четверть блока или раз в 8 тиков. Поворачивается — только больше чем на 3°. Длина луча обновляется, только если изменилась больше чем на 0,2 блока.
4. **Лёгкая синхронизация игрока (`PlayerRpgData.syncTag`).** Клиент получал полный прогресс всех когда-либо сыгранных классов: ранги, модификации, ресурсы, раскладки. Показывает же он из этого только уровень (экран выбора класса). Теперь в пакет уходит только уровень, и пакет для игрока с 5–8 классами становится в несколько раз меньше. Клиентская копия данных никогда не сохраняется и не отправляется обратно, так что потерять ничего нельзя.
5. **Гигиена.** Из проекта удалены мусорные файлы `javac.*.args`, которые раньше попадали в архивы.

## Риски

Риски перечислены по убыванию важности.

1. **Код 3.19–3.25 не компилировался.**
   * Это Посланник, все виды, кролик и этот этап.
   * Вероятнее всего, ошибки будут в сигнатурах Forge и GeckoLib: переопределения, видимость, имена методов mojmap.
   * *Исправление:* первый же лог сборки от автора. Все ошибки компиляции идут вне очереди, до этапа 2.
2. **Конфиг `COMMON` вместо `SERVER`.**
   * Клиент в мультиплеере читает **свой** файл конфига. Множители, лимиты и флаги на сервере и клиенте могут расходиться.
   * Признак проблемы уже в коде: три значения (`rt`, `mpe`, `meq`) пришлось вручную передавать в пакете синхронизации.
   * *Этап 2:* разделить на `SERVER` (баланс, правила; синхронизируется Forge автоматически для мира) и `CLIENT` (HUD, анимации, вспышки), а значения баланса — в JSON-датапак (`data/rpgclasses/balance/*.json`).
3. **Эффекты — это сущности.**
   * Даже с бюджетом каждый эффект стоит пакета появления, данных и трекинга. Летящие снаряды (`bolt`) по-прежнему двигаются сервером каждый тик.
   * *Этап 2:* клиентский менеджер эффектов. Сервер шлёт один пакет «эффект X, тема Y, от A к B, длительность N», а клиент держит пул эмиттеров без сущностей. `SkillFxEntity` остаётся только для эффектов, которые должны пережить выход из зоны прогрузки.
4. **Синхронизация «весь тег».**
   * Ресурсы класса (руническая сила, душа, пси, пустота) меняются почти каждый тик, и из-за них уходит весь тег.
   * *Этап 2:* два канала. Маленький пакет ресурсов каждые 2–5 тиков и полный тег только при смене класса, уровня, рангов, сюжета.
5. **Ожидающее уничтожение реликвии не сохраняется (`GiftedRelic.PENDING`).** Если реликвию уничтожили, пока владелец не в сети, и сервер перезапустился до его входа, владелец не узнает о потере. *Этап 2:* перенести в `SavedData` мира.
6. **26 обработчиков урона.**
   * Каждый сам ищет capability и сам решает, участвует ли игрок.
   * *Этап 2:* один диспетчер урона. Он один раз берёт данные атакующего и жертвы и раздаёт событие только подписанным системам (класс, вид, профессия, группа, броня).
7. **Повторяющийся код навыков.**
   * Восемь классов и 24 Проявления по-своему считают урон, PvP-множитель, кулдаун, эффекты и анимацию.
   * *Этап 2:* единый конвейер силы (`Power`) с шагами `cost → target → effect → fx → anim → cooldown`. На нём и будут строиться подклассы и комбо этапа 5.
8. **Совместимость — в порядке, но без тестов.**
   * Слой `compat/` уже есть: `EpicFightCompat`, `IronsSpellsCompat`, `IronsMana`. Классы обращаются к чужим модам только через него (`EpicFightCompat.isLoaded()`).
   * Проверено это только на «мод не установлен».
   * *Этап 2:* GameTest с подключёнными Iron's Spells и Epic Fight и таблица совместимости в документации.

## Как мерить производительность (для автора)

1. Поставить [spark](https://spark.lucko.me/) (Forge 1.20.1).
2. В мире с 2–4 игроками: `/spark profiler start --timeout 120`, затем 2 минуты боя с AoE-навыками рядом с толпой мобов.
3. `/spark profiler` → ссылка. Нужно смотреть ветки `com.rpgclasses` в `ServerLevel.tick` и `PlayerList`.
4. `/rpg debug` — сколько эффектов создано и пропущено, сколько живёт сейчас, сколько хуков очистки зарегистрировано.
5. Если эффектов не хватает визуально, поднять `fxMaxPerTick` в `config/rpgclasses-common.toml` (раздел `performance`). Если сервер проседает — опустить.

## План этапа 2 (архитектура и производительность)

* `SERVER` / `CLIENT` конфиги и JSON-баланс из датапака с горячей перезагрузкой (`/reload`).
* Клиентский менеджер эффектов, без сущностей для коротких эффектов.
* Разделённая синхронизация игрока: ресурсы и полный тег.
* Диспетчер урона и тика вместо 26 + 9 отдельных подписчиков.
* Конвейер `Power` для навыков классов и Проявлений.
* `SavedData` для состояния, которое должно пережить перезапуск.
* GameTest-тесты (`@GameTest`), запускаемые `gradlew runGameTestServer`: урон навыка, кулдаун, очистка состояния, бюджет эффектов.
