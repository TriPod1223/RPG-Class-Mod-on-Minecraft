# Архитектура (этап 2 тотального обновления, 3.26.0)

Этап 2 перестроил ядро мода, не трогая 8 классов и 24 Проявления изнутри: все они уже шли через общие точки (`Ability.tryUse`, `Combat`, `Fx`), и новое встало именно туда. Поэтому поведение навыков, урон и внешний вид эффектов остались прежними; поменялось то, *как* это работает под капотом.

```
                ┌──────────── сервер ────────────┐            ┌──────────── клиент ────────────┐
 конфиг-файл ─┐ │                                │  RulesSync │                                │
 датапаки ────┴─► Rules.get ──► навыки, урон ... ├───────────►│ Rules.get (значения сервера)    │
                │                                │            │                                │
 Ability.tryUse ► SkillCastEvent.Pre ► cast ► Modifiers (урон, перезарядка) ► SkillCastEvent.Post│
                │                                │            │                                │
 Fx.at/follow…  ► бюджет ► короткий? ──пакет FxSpawn──────────► ClientFx (без сущностей)        │
                │                  └─ длинный: SkillFxEntity  │                                │
 PlayerRpgData  ► syncTag ► дельта ──SyncDelta / Sync────────► база + слияние ► readSync       │
                └────────────────────────────────┘            └────────────────────────────────┘
```

## 1. Правила: конфиг → датапак → клиент (`config/Rules`)

**Было.** Каждое из 152 мест читало `RpgConfig.X.get()`. В мультиплеере клиент читал **свой** файл конфига, поэтому меню, подсказки и клиентские проверки могли расходиться с сервером: включён ли Одарённый, можно ли сменить вид, размер группы и т. д.

**Стало.** Все чтения идут через `Rules.get(RpgConfig.X)`. Эффективное значение:

* на **сервере** — файл `config/rpgclasses-common.toml`, поверх него — переопределение из датапака;
* на **клиенте** — значения сервера (приходят при входе, после `/reload` и после каждого изменения на экране баланса); до входа в мир — собственный файл.

`validate.py` запрещает прямое `RpgConfig.X.get()` в новом коде.

**Личные настройки клиента** переехали в отдельный файл `config/rpgclasses-client.toml` (`RpgClientConfig`):

* смещение HUD (`hud.hudOffsetX/Y`);
* предел одновременно рисуемых эффектов (`effects.maxSkillEffects`, по умолчанию 384);
* дальность отрисовки эффектов (`effects.skillEffectDistance`, 96).

Старые `client.hudOffsetX/Y` из common-файла больше не читаются: смещение HUD нужно один раз выставить заново.

> Почему не тип конфига `SERVER`. Он хранится в каждом мире отдельно (`saves/<мир>/serverconfig`), и при переходе у всех пропали бы текущие настройки. Кроме того, до входа в мир его значения недоступны, а часть кода читает настройки в меню. `Rules` даёт то же самое — сервер решает, клиент видит — без переноса файла.

### Баланс из датапака

Файлы `data/<любое_пространство>/rpgclasses_balance/<имя>.json` — объект «настройка → значение». Настройка задаётся по полному пути (`classPvp.pvpFactorDeathKnight`) или по последнему имени (`pvpFactorDeathKnight`): в конфиге нет двух настроек с одинаковым именем, `validate.py` это проверяет.

```json
{ "pvpDamageMultiplier": 0.5, "classPvp.pvpFactorSpellbreaker": 1.2, "giftedEnabled": false }
```

Правила применения:

* Файлы применяются по порядку их id, поэтому при совпадении ключей побеждает более поздний.
* Тип и диапазон проверяются по описанию настройки. Неизвестный ключ, неверный тип или выход за диапазон — предупреждение в логе и пропуск, а не падение.
* Списки и тексты (например, `professionBans`) датапаком не переопределяются.
* `/reload` перечитывает файлы и сразу рассылает новые значения всем клиентам.
* Файл конфига датапак **не трогает**. Экран баланса (`/rpg balance`) по-прежнему пишет в файл, но значение из датапака сильнее и показывается как текущее.
* `/rpg debug` показывает, сколько настроек переопределено. Сам список пишется в лог при загрузке.

Готовый пример: `docs/examples/balance_datapack/` — положите папку в `saves/<мир>/datapacks/`.

## 2. Эффекты без сущностей (`client/ClientFx`)

**Было.**

* Каждый эффект навыка был серверной сущностью `SkillFxEntity`: пакет появления, синхронизируемые данные, отслеживание, движение каждый тик, удаление.
* Этап 1 добавил бюджет (`fxMaxPerTick`) и отсечение по игрокам (`fxCullDistance`), но цена одного эффекта осталась прежней.

**Стало.**

* Короткий эффект (до 200 тиков, то есть почти все) — это один пакет `FxSpawn` (~40–70 байт) игрокам в радиусе отсечения.
* Клиент держит у себя **отсоединённую** копию `SkillFxEntity`. Она создана на клиенте и не добавлена в мир, поэтому мир её не тикает и не отслеживает.
* Каждый клиентский тик копия движется по тем же правилам, что и раньше на сервере:
  * приклеена к сущности;
  * летит снарядом;
  * луч между двумя сущностями, рвётся дальше `maxLen`.
* Рисуется тем же `SkillFxRenderer` и теми же анимациями GeckoLib после частиц. Внешне эффекты не изменились.

Детали:

* Пакет может прийти раньше сущности, к которой эффект приклеен (снаряд, созданный в этот же тик). Поэтому в первые 20 тиков эффект ждёт её появления.
* Длинные ауры (венец Рыцаря Смерти, метки) остаются сущностями: их держат и снимают сами навыки. Для таких мест есть `Fx.followKept(...)` — всегда сущность.
* Вызовы, которым раньше нужна была возвращённая сущность, получили параметры:
  * поворот разреза: `Fx.at(..., roll)`;
  * предел длины щупальца: `Fx.beam(..., maxLen)`.
* Если отрисовка на клиенте упадёт, клиент один раз пишет ошибку в лог и до следующего входа перестаёт рисовать клиентские эффекты. Игра продолжается.
* Аварийный выключатель на сервере: `performance.clientSideEffects = false` возвращает старое поведение «каждый эффект — сущность».

## 3. Дельта-синхронизация данных игрока

**Было.**

* Пока данные «грязные» (а ресурсы классов меняются почти каждый тик), клиенту до 4 раз в секунду уходил весь тег: класс, ранги, сюжет, профессии, вид, раскладки.
* Этап 1 уже убрал из него прогресс остальных классов.

**Стало.**

* Сервер помнит, что клиент уже знает (`NetworkHandler.LAST`), и шлёт только изменившиеся части верхнего уровня: обычно `extra`, `rp`, `cd`, `runes`, `combat`. Исчезнувшие ключи передаются списком.
* Клиент сливает изменения в свою базу и применяет её целиком. Код, который читает `PlayerRpgData`, ничего не заметил.
* Полная синхронизация уходит:
  * при входе;
  * при возрождении;
  * при смене измерения (у клиента новый объект игрока);
  * после выхода — база забывается.

`/rpg debug` показывает число полных и дельта-пакетов, а также сколько неизменных частей не было отправлено.

## 4. Конвейер навыков: события и модификаторы

**`api/SkillCastEvent`** — событие на шине Forge вокруг каждого навыка класса (`Ability.tryUse`) и каждого Проявления Одарённого:

* `Pre` — все проверки пройдены, ничего ещё не произошло. Событие можно отменить, по желанию — с сообщением (`deny("lang.key")`).
* `Post` — навык сработал. Анимация, вспышка и перезарядка уже выставлены. Событие сообщает длительность перезарядки и для Проявлений число задетых существ.

На этих событиях строятся подклассы и комбо этапа 5. Аддону не нужно править навыки:

```java
MinecraftForge.EVENT_BUS.addListener((SkillCastEvent.Post e) -> {
    if (e.skill().getPath().equals("death_strike")) Combo.push(e.player(), "strike");
});
```

**`core/Modifiers`** — множители урона навыков и перезарядок игрока. Раньше это были строки, прошитые в `Combat` и `Ability`; теперь это именованный список:

* встроенные, в прежнем порядке и с прежними значениями:
  * `rpgclasses:class` — комбо, ярость;
  * `rpgclasses:class_relic`;
  * `rpgclasses:party_synergy`;
  * `rpgclasses:gifted`;
  * `rpgclasses:gifted_time` — перезарядка;
* новые подключаются одной строкой: `Modifiers.damage("addon:rage", (p, d, c, t) -> ...)`; повторная регистрация того же id заменяет множитель;
* `/rpg debug damage` при взгляде на существо показывает, во что превращаются 100 единиц урона, и каждый множитель по отдельности.

Глобальный множитель урона навыков и PvP-факторы остались в `Combat.scaled`.

## 5. Состояние, которое переживает перезапуск

`kind/GiftedWorldData` (`SavedData` верхнего мира, файл `data/rpgclasses_gifted.dat`) хранит реликвии, уничтоженные, пока владельца не было в сети. Раньше это лежало в статической карте, и перезапуск сервера до входа владельца терял событие.

## 6. Автотесты (GameTest)

`gametest/RpgGameTests` — 6 тестов ядра без игрока:

* правила читают конфиг;
* датапак проверяет тип и диапазон;
* `Combat.scaled` для мобов;
* бюджет эффектов отсекает невидимое, но не трогает длинные ауры;
* `GiftedWorldData` выдаёт реликвию ровно один раз;
* реестры модификаторов и очистки заполнены.

Как запускать:

* `gradlew runGameTestServer` — сервер запускается, проходит все тесты и останавливается. Если тест упал, задача Gradle падает.
* В мире разработки (`runClient`): `/test runall`.
* Шаблон 3×3×3 с каменным полом лежит в `data/rpgclasses/structures/empty.nbt` (генерирует `tools/gen_test_structure.py`).
* У игроков тесты не регистрируются.

## Что сознательно не делалось на этом этапе

* **Единый диспетчер урона вместо 26 обработчиков `LivingHurt`.** У каждого обработчика свой порядок и свои условия отмены. Переносить их без запуска игры — значит рисковать тихими изменениями баланса. Сделаю на этапе 5 вместе с переносом навыков на конвейер, когда будет первая успешная сборка и тесты.
* **Перенос навыков классов в описания-данные (JSON).** Тоже этап 5: сначала конвейер должен доказать себя на подклассах.
